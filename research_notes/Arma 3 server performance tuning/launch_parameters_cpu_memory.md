# Arma 3 Windows dedicated server: launch parameters, CPU and memory settings (2.20 / 2.22)

Scope: `arma3server_x64.exe` on a Windows host with a modern CPU of 6 or more cores and 32 GB or more of RAM, running a heavily modded ACE/CBA milsim server for 40–80 players. Researched 2026-11-19.

How the sources were reached. The Bohemia wiki (community.bistudio.com and community.bohemia.net) and forums.bohemia.net both sent a Cloudflare challenge or HTTP 403 to every direct fetch, so all wiki and forum pages below were read from Wayback Machine snapshots. Each citation gives the snapshot date and the page's "last edited" date. Pages on dev.arma3.com, GitHub, Steam and Microsoft Learn were fetched directly.

Source labels used below:
- **BI-official**: Bohemia dev blog, SPOTREP changelogs, posts by BI developers (Dedmen, Dwarden, DnA), or wiki text describing engine behaviour.
- **Wiki-community**: wiki text written from community testing, such as the "Observed Behaviour" section.
- **Community**: guides, gists, forum and Steam posts by players and admins.
- **Excerpt-only**: seen only in a search-engine summary because the page itself could not be retrieved. Treat as unverified.

## Q1. Which parameters are auto-detected well enough on 2.20/2.22 that setting them changes nothing (-exThreads, -cpuCount)?

### Takeaway
Bohemia now says plainly that `-exThreads` "should not be used" and that `-cpuCount` is only for deliberately *limiting* cores, because the engine detects core count itself. On a 6+ core host both parameters are auto-detected. Setting them gains nothing, and `-cpuCount` silently disables `-enableHT`. A hand-set `-cpuCount` has also caused at least one bug in the new job system (a freeze with `-cpuCount=2` on a Nov-2024 experimental build, since fixed). `-maxMem` is also auto-set, and the wiki advises leaving it out (see Q7).

### Cited Findings
- **BI-official, OPREP for 2.20, Dedmen, 17 Jun 2025.** Bohemia says "the -exThreads parameter should not be used." On CPUs with 4 or more cores all exThreads are already enabled by default; on CPUs with fewer than 4 cores, extra exThreads are more likely to cause harm. — [OPREP – Performance Optimizations in 2.20](https://dev.arma3.com/post/oprep-performance-optimizations-in-220)
- **BI-official, same post.** Use `-cpuCount` only "if you want to intentionally limit how many CPU cores the game can use". The engine detects core count automatically. The one stated exception: if an external tool restricts process affinity, "you need to use -cpuCount to inform the game about how many cores it can actually use." — [OPREP 2.20](https://dev.arma3.com/post/oprep-performance-optimizations-in-220)
- **BI-official, same post (paraphrased).** The post says feedback from the Profiling branch showed players misusing command-line parameters, and that is why it includes launch-parameter guidance. Its benchmarks were client-side (YAAB frame-time graphs, no FPS numbers), and the post does not discuss dedicated servers. — [OPREP 2.20](https://dev.arma3.com/post/oprep-performance-optimizations-in-220)
- **BI-official, wiki.** `-cpuCount`: "Change to a number less or equal than numbers of available cores. This will override auto detection (which equate to native cores)." Since 2.20, "The minimum value is 2." — [Arma 3: Startup Parameters, Wayback snapshot 2026-06-17, page edited 10 May 2026](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official, wiki.** `-exThreads`: "Change to a number 0,1,3,5,7. This will override auto detection (which use 3 for dualcore and 7 for quadcore)." The thread offloads file operations, geometry loading and texture loading from the main thread "however it adds some overhead at the same time." — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official, 2.20 changelog.** 2.20 "Replaced Real Virtuality multithreading job system with Enfusion's version". It also added multithreaded JIP queue processing, partially multithreaded AI simulation, multithreaded AI visibility, AI sensor and target-list scanning, PhysX, trigger-area scanning, and `nearestObjects`/`nearObjects`/`allMissionObjects` internals. — [SPOTREP #00118 (2.20)](https://dev.arma3.com/post/spotrep-00118)
- **BI-official, profiling branch Nov 2024.** On the then-experimental Enfusion job system, Dedmen's v13 notes (26 Nov 2024) list "Fixed: Freeze with -cpuCount=2 (thanks Gold John King)". This shows that a hand-set `-cpuCount` interacts with the job system and was a source of bugs. — [Profiling thread p.107, Wayback 2025-02-02](http://web.archive.org/web/20250202170530/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=107)
- **Community (paraphrased).** XenyxNZ says to use CPU count only to limit cores (unchecked, the game uses all physical cores) and to leave Extra threads disabled because the game already detects core count. — [XenyxNZ Arma-3-Performance-Guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)
- **Community.** A Steam thread from 18–22 Jun 2025 asked whether old launch lines (`-cpuCount=8 -exThreads=7 -maxMem=31744 ...`) still matter after 2.20. The only answer reposted the OPREP guidance. No BI developer replied and nobody posted test results. — [Steam: "Should i still use launch commands on new patch 2.20?"](https://steamcommunity.com/app/107410/discussions/14/591774445091225273/)

### Inferences
- Agreement: BI (OPREP plus wiki) and one independent community guide (XenyxNZ) agree on leaving `-exThreads` and `-cpuCount` unset. The Steam thread only relays OPREP, so it is not independent. No source argues for setting them on 2.20+.
- On a dedicated server there is no rendering, so the geometry and texture loading roles of `-exThreads` matter little (an inference from the wiki's description). There is even less reason to set it on a server than on a client.
- **Preset value:** leave out `-exThreads` and `-cpuCount`. Offer `-cpuCount` only as an advanced field for hosts that restrict affinity externally (`start /affinity`, Task Manager, a VM), with a note that it must match the allowed core count and disables `-enableHT`.

### Gaps
- No server-side benchmark (server FPS before and after) of `-exThreads` or `-cpuCount` on 2.20+ was found. BI's numbers are client YAAB graphs.
- The wiki's exThreads table shows which loading threads each value enables as icons, not text, so the per-value mapping could not be extracted from the snapshot.

## Q2. Does -enableHT help or hurt a server, and does -cpuCount override it?

### Takeaway
Yes, `-cpuCount` overrides it: `-enableHT` is ignored when `-cpuCount` or (since 2.22) `-cpuAffinity` is set. Bohemia's own tests found `-enableHT` "performs worse", though hardware-dependent. Community guides are split, and no server-specific measurement exists. The safe default is off, offered as a toggle the admin can A/B test.

### Cited Findings
- **BI-official, OPREP 2.20.** "The -enableHT parameter has no effect if -cpuCount is set, so setting both is wrong." "Our tests have shown that -enableHT performs worse, but it may depend on your hardware." The post suggests testing with YAAB. — [OPREP 2.20](https://dev.arma3.com/post/oprep-performance-optimizations-in-220)
- **BI-official, wiki.** `-enableHT` "Enables the use of all logical CPU cores for parallel tasks processing… When disabled, only physical cores are used." It "may slightly improve or harm the performance depending on a scenario," and "This parameter is overridden if -cpuCount or -cpuAffinity are used so if you want to use the maximum number of CPU cores use '-enableHT' without '-cpuCount'." — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official, profiling build Nov 2024 (experimental, superseded).** Dedmen's 2.18 profiling v8 notes listed "KNOWN ISSUE: If your game is crashing at start or mission load, set -cpuCount to a value below 12, and turn off hyperthreading/-enableHT." That applied to the experimental Enfusion job system before it reached stable 2.20. It is not current guidance, but it shows high logical-core counts once triggered crashes. — [Profiling thread p.106, Wayback 2024-11-06](http://web.archive.org/web/20241106123403/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=106&tab=comments)
- **Community, conflicting (paraphrased).** XenyxNZ generally recommends Hyper-Threading on. It says disabling it on CPUs with 8 or more cores can sometimes give slightly more performance, recommends a YAAB benchmark, and notes it is ignored when CPU count is set. — [XenyxNZ guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)
- **Community, conflicting.** A community gist's server launch line includes `-enableHT`, with no measurement given: `-hugepages -maxMem=16000 -malloc=mimalloc_v203_LockPages -enableHT -bandwidthAlg=2 -limitFPS=500 -loadMissionToMemory`. — [MildlyInterested "Arma useful things" gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **Wiki-community, Dedicated Server page.** On a physical Intel CPU "the odd numbered CPUs are Hyper-thread cores". The page also says "the bulk of processing is used up by only one or two threads… There is one thread in the process that handles all of the AI units". That text predates 2.20, which made AI simulation partially multithreaded. — [Arma 3: Dedicated Server, Wayback 2026-06-17, page edited 22 May 2026](http://web.archive.org/web/20260617130649/https://community.bohemia.net/wiki/Arma_3:_Dedicated_Server); [SPOTREP #00118](https://dev.arma3.com/post/spotrep-00118)

### Inferences
- Agreement: one BI source (backed by the wiki) says HT is "worse in our tests". One community guide says "generally on, sometimes worse on 8+ cores", and one community config uses it without data. That is a two-way split, with BI's measured statement the strongest evidence.
- BI's test was a client benchmark. Applying it to a dedicated server is an inference: a server has no render work, so fewer parallel jobs can use the extra logical cores, which if anything weakens the case for HT.
- **Preset value:** leave `-enableHT` out of the "Maximum" preset by default and expose it as an opt-in toggle labelled "test with your mission". The panel should refuse, or warn on, `-enableHT` together with `-cpuCount` or `-cpuAffinity`, because BI says that combination is "wrong" and it does nothing.

### Gaps
- No server FPS measurement with and without `-enableHT` on 2.20/2.22 was found from BI or the community.
- Whether the Nov-2024 "cpuCount ≥12 plus HT crash" was fully fixed before 2.20 stable is not stated in the pages retrieved. No such known issue appears in the 2.20 SPOTREP lines that were checked.
- No Reddit threads could be retrieved, because searches surfaced none.

## Q3. What does -hugePages require on Windows, what happens without it, which -malloc pairs with it, and is the "LockPages" mimalloc variant meant for servers? Which allocators ship today?

### Takeaway
Large pages on Windows need the **"Lock pages in memory" user right (SeLockMemoryPrivilege)** granted to the account that runs the server, followed by a re-logon or reboot. The memory is then non-pageable and must be contiguous, so allocation is best done at startup. The most recent retrievable BI documentation (wiki revision of Oct 2024) lists `tbb4malloc_bi` (the default) and `jemalloc_bi` as the shipped allocators. The mimalloc builds in circulation are third-party DLLs (GoldJohnKing). One unconfirmed search excerpt says a Feb-2026 Profiling build added a mimalloc allocator, and what ships with 2.22 stable was not verified. The "LockPages" variants were made for large-memory *client* PCs and were not recommended even by their author. They were dropped in January 2025, and current builds use large pages automatically when the privilege is present. A community-observed note on BI's wiki says a dedicated server may gain little from a custom allocator.

### Cited Findings
**What ships with the game / defaults**
- **BI-official, wiki (revision of 21 Oct 2024).** The default allocator "is based on Intel TBB 4". The search order in the `dll` folder next to the exe is `tbb4malloc_bi` (TBB 4, tbb2017_20160916oss), then `jemalloc_bi` (jemalloc 4.3.1), then `customMalloc_bi` (not provided). With no DLL present the engine falls back to Windows `_aligned_malloc`. `-malloc=system` forces the Windows allocator. The `-malloc` value has the dll directory and extension appended automatically, and the name "must not contain any dots before the .dll extension". — [Arma 3: Custom Memory Allocator, Wayback 2025-04-28, rev. 369956 edited 21 Oct 2024](http://web.archive.org/web/20250428011956/https://community.bohemia.net/wiki/Arma_3:_Custom_Memory_Allocator)
- **BI-official, wiki.** "You can specify allocator for Windows dedicated server the same way as for client binary… with specifically adjusted memory allocator you may experience performance gains, for example with Large Pages support or ability define huge pre-allocation memory regions". The Linux server always uses the OS allocator. — [Custom Memory Allocator (Wayback 2025-04-28)](http://web.archive.org/web/20250428011956/https://community.bohemia.net/wiki/Arma_3:_Custom_Memory_Allocator)
- **BI-official, 2016.** BI stopped distributing TCMalloc_bi, NedMalloc_bi, JEMalloc_bi and tbb3malloc_bi, and kept tbb4malloc_bi and JEMalloc_bi as the supported defaults. (The post lists JEMalloc_bi in both groups.) Any other allocator can still be loaded with `-malloc=` but is "experimental". — [SITREP #00177, 11 Oct 2016](https://dev.arma3.com/post/sitrep-00177)
- **Excerpt-only (unverified).** A search summary of the wiki page "Arma 3: Prof-Branch Change Log v2.20" reported build 2.20.153560 (profiling v54, 18 Feb 2026) with "Added: Mimalloc memory allocator". The page returned 403 and the Wayback Machine holds no snapshot of it (checked for both wiki hosts while the archive was online), so this could not be confirmed. "Allocator" or "malloc" appears nowhere in the 2.22 main-branch changelog (SPOTREP #00120, 11 Aug 2026) or its hotfixes #00121/#00122. — [Prof-Branch Change Log v2.20 (not retrieved)](https://community.bistudio.com/wiki/Arma_3:_Prof-Branch_Change_Log_v2.20); [SPOTREP #00120](https://dev.arma3.com/post/spotrep-00120); [SPOTREP #00121](https://dev.arma3.com/post/spotrep-00121); [SPOTREP #00122](https://dev.arma3.com/post/spotrep-00122)

**-hugePages and the Windows privilege**
- **BI-official, wiki.** `-hugePages`: "Enables hugepages with the default memory allocator (malloc) for both client and server." The Custom Memory Allocator page says: "To enable allocator to use Large Pages instead of Small Pages start game with commandline switch -hugepages". The DLL interface exposes an optional `EnableHugePages()`, "Called before the first allocation". — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters); [Custom Memory Allocator (Wayback 2025-04-28)](http://web.archive.org/web/20250428011956/https://community.bohemia.net/wiki/Arma_3:_Custom_Memory_Allocator)
- **Microsoft.** Using large pages requires obtaining **SeLockMemoryPrivilege** (via `AdjustTokenPrivileges`) and allocating with `VirtualAlloc(MEM_LARGE_PAGES)`, with size a multiple of `GetLargePageMinimum`. Large-page memory "may be difficult to obtain after the system has been running for a long time because the physical space for each large page must be contiguous". Applications "should… allocate all large pages one time, at startup". The memory "is always read/write and nonpageable (always resident in physical memory)" and is not part of the working set. — [Microsoft Learn: Large-Page Support](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)
- **Community, setup steps (paraphrased).** Open gpedit.msc, go to Computer Configuration > Windows Settings > Security Settings > Local Policies > User Rights Assignment, open "Lock pages in memory", add the accounts or groups (the guide adds Administrators and Users), then restart. The guide says this needs Windows Pro/Enterprise/Education and that Windows does not grant the privilege by default. — [XenyxNZ guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)
- **Excerpt-only.** A search summary paraphrased a guide as saying that, by default, a Windows profile lacks the privileges to use large pages even when the parameter is enabled. The guide was not identified with certainty, though it is probably XenyxNZ. — [XenyxNZ guide (probable)](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)
- **Community, allocator author.** From mimalloc Arma-3-v2.1.7-20250103: mimalloc "always tries to reserve Large Pages (up to 1GiB per page) when necessary, regardless of whether you toggle Enable Large-page Support… or append -hugePages… as long as your system is configured properly". It links Microsoft's "Enable the Lock pages in memory option". — [GoldJohnKing/mimalloc release Arma-3-v2.1.7-20250103](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v2.1.7-20250103)

**LockPages variants: what they were and who they were for**
- **Community, allocator author, Dec 2021.** "If you have a large memory and always have more than 8GB free memory space before you run Arma 3, you may try `mimalloc_v203_LockPages.dll`, as it would lock several continuous 1GB large pages in your physical memory". The general-use file was `mimalloc_v203.dll`. — [GoldJohnKing release Arma-3-v2.0.3-20211230](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v2.0.3-20211230)
- **Community, allocator author, Apr 2023 to Nov 2024.** The `_lock_pages` variant "locks up to 8 consecutive 1GB large pages… Personally I won't recommend it, as it consumes huge amount of memory but only provides a little bit more performance gain". The `_no_collect` variant was for users with frequent `STATUS_ACCESS_VIOLATION` crashes. — [Release Arma-3-v2.1.2-20230427](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v2.1.2-20230427); [Release Arma-3-v2.1.7-20241117](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v2.1.7-20241117)
- **Community, allocator author, Jan 2025.** "Large Pages are always locked in physical memory… So, forget about lock-pages variants provided in previous releases, as it is always the default behavior." The no-collect and scheduled-collect variants were also removed as "proven to have no benefits". — [Release Arma-3-v2.1.7-20250103](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v2.1.7-20250103)
- **Naming history** (GitHub releases API): `mimalloc_v203_LockPages.dll` and `mimalloc_v205_LockPages.dll` (2021–22); `mimalloc-v206-lock-pages.dll` through `mimalloc-v209-lock-pages.dll` (2022–23); `mimalloc_v212_lock_pages.dll` through `mimalloc_v217_lock_pages.dll` (2023–24); single files after that, e.g. `mimalloc_v219_20250213.dll`. The latest are `mimalloc_v360_20261024.dll` (25 Oct 2026, v3 line) and `mimalloc_v250_20260820.dll` (20 Aug 2026, v2 line). — [GoldJohnKing/mimalloc releases](https://github.com/GoldJohnKing/mimalloc/releases)
- **Community, author's own claims, not independently measured.** v2.0.x releases claimed "5-15%" over BI's TBB4. Current releases claim "up to 30% higher FPS than default memory allocator while significantly improves the worst case FPS". The v3.1.5 release (Jul 2025) warned that "mimalloc v3.x.x is still in beta… You should prefer v2.x.x for now". v2.1.7-20241117 was marked deprecated because it "does no performance gain than default TBB memory allocator". From v2.4.1/v3.4.1 (Jul 2026), env-var options use the prefix `ARMA3_MIMALLOC_*` to avoid clashing with the mimalloc embedded in NVIDIA drivers. — [Release v2.0.6-20220419](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v2.0.6-20220419); [Release v3.6.0-20261024](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v3.6.0-20261024); [Release v3.1.5-20250703](https://github.com/GoldJohnKing/mimalloc/releases/tag/Arma-3-v3.1.5-20250703)

**Does a server benefit at all?**
- **BI-official quote embedded in the wiki.** Dedmen: "Arma has multiple internal allocators. The pool allocator used for all of scripting does not respect large pages flag, but these don't allocate that often." — [Custom Memory Allocator (Wayback 2025-04-28)](http://web.archive.org/web/20250428011956/https://community.bohemia.net/wiki/Arma_3:_Custom_Memory_Allocator)
- **Wiki-community, "Observed Behaviour" section from community testing.** "a server rarely takes more than 2GB", and "A Dedicated server may not take advantage of custom allocator as well, as the total page size allocated by server is always equal to reserved huge pages size + active physical memory, which means it does not allocate through CMA at all." — [Custom Memory Allocator (Wayback 2025-04-28)](http://web.archive.org/web/20250428011956/https://community.bohemia.net/wiki/Arma_3:_Custom_Memory_Allocator)
- **BI-official.** 2.20 "Optimized the game's memory usage (~400 MB…)" and made "Several memory allocation optimizations". — [SPOTREP #00118](https://dev.arma3.com/post/spotrep-00118)
- **Community server configs (paraphrased).** The gist pairs `-hugepages` with `-malloc=mimalloc_v203_LockPages` on `arma3server_x64`. It says the allocator was tested up to v206 and that v209 has reported stability problems. — [MildlyInterested gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **Community, client context (paraphrased).** XenyxNZ warns that a newly released mimalloc DLL can show a "Blocked loading of file" error until BattlEye whitelists it, which can take a few days. — [XenyxNZ guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)
- **Excerpt-only, source page not identified.** A search summary attributed to BI developer Dwarden the statement that hugepages give roughly a 1–15% performance boost, depending on CPU cache sizes, architecture and memory latency. The candidate is the xtbbmalloc forum thread, which could not be retrieved. — [xtbbmalloc thread p.2 (candidate, not retrieved)](https://forums.bohemia.net/forums/topic/191816-xtbbmalloc-a-custom-memory-allocator-for-a3/?page=2)
- **Excerpt-only, source page not identified.** A search summary mentioned a Steam user who tested mimalloc after 2.20, found small gains plus system instability and more crashes, and went back to the default. Candidates: [Steam "arma 3 best memory allocator 2023"](https://steamcommunity.com/app/107410/discussions/0/3806156942405780446/), [Steam "5600X vs 5800X3D - And different memory allocators too!"](https://steamcommunity.com/app/107410/discussions/0/3817418793975390255/). Neither page was retrieved.

### Inferences
- **Pairing:** `-hugePages` works with BI's default `tbb4malloc_bi`; the wiki says it enables large pages "with the default memory allocator". You do not need `-malloc` to use it. Current GoldJohnKing mimalloc builds use large pages whenever the privilege is present, with or without `-hugePages`.
- **Is LockPages "meant for servers"?** No. It was a client-oriented variant for large-RAM PCs that its own author did not recommend, and it has not existed since January 2025. The v2.0.6 release assets are named `mimalloc-v206-lock-pages.dll`, not `mimalloc_v206_LockPages` (the underscore/CamelCase form was used only for v1.7.3–v2.0.5). A panel must not hard-code any mimalloc name. It should list the DLLs actually present in `<server>\Dll\` and pass the chosen base name (no extension, no dots) to `-malloc=`.
- **Without the privilege:** under Microsoft's API, `VirtualAlloc(MEM_LARGE_PAGES)` without SeLockMemoryPrivilege fails. The flag would then most likely have no effect, with the allocator falling back to normal pages. This is an inference, not verified for Arma.
- **Server-side benefit is the least proven setting in the list.** BI's wiki (community-observed) doubts that servers allocate through the CMA much, scripting's pool allocator ignores large pages, and every performance figure is either a client figure or the allocator author's own claim. Agreement: 3 community sources recommend mimalloc plus large pages (XenyxNZ, the gist, GoldJohnKing), none with server measurements. BI has not endorsed any third-party allocator.
- **Preset value:** include `-hugePages` only if the panel can verify that the service account holds SeLockMemoryPrivilege (e.g. via `whoami /priv` run as that account). Otherwise leave it out and show setup instructions. Leave `-malloc` unset, which means `tbb4malloc_bi`, in the default "Maximum" preset. Offer a dropdown filled from the Dll folder for admins who install mimalloc themselves, with warnings about the reported crash risk and a possible BattlEye whitelisting delay. The BattlEye delay was reported for clients, so whether it applies to a BattlEye-enabled server is an inference. On a 32 GB host, locked non-pageable memory counts against the RAM available to headless clients on the same box (inference from Microsoft's "nonpageable" description).

### Gaps
- The current contents of the 2.22 `Dll` folder could not be checked: there is no local Arma 3 or Arma 3 Server install on this machine (only Arma 3 Tools), and the latest Custom Memory Allocator wiki snapshot is the October 2024 revision. Whether BI now ships a mimalloc DLL (the unverified Feb-2026 profiling claim) remains unconfirmed.
- What Arma writes to the RPT when `-hugePages` is set without the privilege (silent fallback, warning or failure) is not documented in any source found.
- No server FPS comparison of tbb4malloc_bi against mimalloc, or with and without hugePages, on 2.20/2.22 was found.
- Dwarden's 1–15% statement could not be retrieved (forum 403 and no archive fetch).

## Q4. What do admins report for raising the server's -limitFPS (100, 120, 1000)? Does it help AI and scripts or just burn CPU?

### Takeaway
BI documents that raising the limit makes the server send network messages and simulate entities and AI more often, but "the practical impact… may or may not [be] noticeable", and "the limit does not do anything when it is not reached." Whenever the server is already running below the cap, as is likely under heavy load (an inference for a modded ACE server with 40–80 players and AI), a higher cap changes nothing. The only real-data test (2017, custom binaries) showed big gains only on idle servers and none with 200 AI. Since 2.20 an empty server is capped at 30 FPS anyway, and 2.22 adds `idleFPSLimit`.

### Cited Findings
- **BI-official, wiki.** Since 2.00, `-limitFPS` "Adjusts the FPS limit for the dedicated server/headless client… The current default is 50. The available range goes from 5 to 1000." "The limit does not do anything when it is not reached." "Higher FPS for a DS/HC [means] network messages sent out more frequently, entities… are simulated more often, as well as AI behavior and vision calculations are done more often. The practical impact of a higher fps limit for the DS/HC may or may not noticeable." — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official, 2.20 changelog.** "Servers with no players now limit their FPS to 30 (regardless of -limitFPS parameter)", and "-limitFPS command-line parameter now also works on clients". — [SPOTREP #00118 (2.20)](https://dev.arma3.com/post/spotrep-00118)
- **BI-official, 2.22 changelog.** "Added: idleFPSLimit server config to limit maximum FPS while a server is empty". — [SPOTREP #00120 (2.22, 11 Aug 2026)](https://dev.arma3.com/post/spotrep-00120)
- **BI developer, 2017 test before the parameter existed.** Dedmen published unofficial server binaries with the 50 FPS cap raised: "This DOES NOT INCREASE SERVER PERFORMANCE. It simply removes the 50 fps limit. Meaning if your server was running with <50 fps before it will still run exactly the same." He added: "It could completly fuck up simulation, physx or AI… That's why I published it so we can get some research data". — [Forum "Server FPS limit testing" p.1, 13–14 Sep 2017, Wayback 2024-04-21](http://web.archive.org/web/20240421115300/https://forums.bohemia.net/forums/topic/210492-server-fps-limit-testing/)
- **Community measurement, same thread.** User Flax, on Malden with 4 players: no AI, server FPS went from 46 (stock) to 168 (200-FPS binary), with client FPS roughly unchanged (86/52/90/71 vs 83/54/88/71). With 100 vs 100 AI in town, server FPS went from **21 to 19**, with clients 23–25 vs 22–27. "Once you start putting lots of AI down it doesn't seem to make much difference." — [Server FPS limit testing p.1 (Wayback 2024-04-21)](http://web.archive.org/web/20240421115300/https://forums.bohemia.net/forums/topic/210492-server-fps-limit-testing/)
- **Community, same thread.** One user saw larger swings in server FPS (from about 3 to 150) and called running a server at 180 FPS "useless". Another reported going from 17 to 83 FPS on a modded Takistan server, but other posters questioned the claim: the screenshot looked idle, and the user had made "a few other tweaks" at the same time. — [Server FPS limit testing p.1 (Wayback 2024-04-21)](http://web.archive.org/web/20240421115300/https://forums.bohemia.net/forums/topic/210492-server-fps-limit-testing/)
- **BI developer, same thread.** Dwarden (14 Sep 2017): "there is no link in FPS between client and server… if server is below 20, it's very wrong… but if server runs e.g. 40 fps then client can run 60 (or 100 or more…)". — [Server FPS limit testing p.1 (Wayback 2024-04-21)](http://web.archive.org/web/20240421115300/https://forums.bohemia.net/forums/topic/210492-server-fps-limit-testing/)
- **Community config.** The gist uses `-limitFPS=500` with no measurement. — [MildlyInterested gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **Excerpt-only (unverified), later pages of the same thread.** One admin reportedly found that a cap of 100 reduced desync and AI rollback while AI was spawning. Another found 100 made the server drop to about 25 FPS, and only 60 worked, raising it from about 47–48 to 59–60. — [Server FPS limit testing p.6 (not retrieved)](https://forums.bohemia.net/forums/topic/210492-server-fps-limit-testing/?page=6)

### Inferences
- Agreement: BI (wiki and two developers) and the only numeric community test agree that a higher cap does not add capacity and helps only when the server already has headroom above 50. Anecdotes of "smoother" play exist but are confounded. Three configs or anecdotes favour a high cap (gist at 500, the excerpt-only "100 helped", Ry4nD), none controlled.
- Above the cap, the main thread runs flat out. On a shared host this takes CPU time from headless clients on the same machine (inference from the 2017 report of FPS climbing to the cap). Idle burn is now limited by the 2.20 30-FPS empty-server rule and the 2.22 `idleFPSLimit`.
- The 2017 data predate 2.00 (custom binaries) and 2.20's multithreading, so they show direction only.
- **Preset value:** the evidence-neutral value is the default, 50. A moderate cap such as `-limitFPS=100` is defensible for "Maximum", because it is reversible and has a measurable effect only when the server has spare headroom. Note, though, the unverified report (p.6 excerpt above) that 100 dropped one server to about 25 FPS while 60 worked. Values like 500 or 1000 have no supporting evidence. Pair the cap with `idleFPSLimit` in server.cfg (2.22). Expect no change during heavy ACE ops where server FPS is already below 50.

### Gaps
- No 2.20/2.22-era measurement of `-limitFPS` above 50 on a modded server was found.
- The later pages of the forum thread (including the 100-vs-60 anecdotes) and any Reddit threads could not be retrieved.

## Q5. Is -bandwidthAlg=2 still experimental, and do admins report better or worse results?

### Takeaway
Yes. The current (May 2026) wiki still calls it "a new experimental networking algorithm that might be better than the default one". No BI data, changelog note or controlled community test showing a benefit was found. Admin reports are anecdotal and mixed, so it does not belong in a default "Maximum" preset.

### Cited Findings
- **BI-official, wiki (edited 10 May 2026).** `-bandwidthAlg`: "Set to 2 to use a new experimental networking algorithm that might be better than the default one." Example: `arma3_x64.exe -bandwidthAlg=2`. — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official.** The 2.22 netcode changes ("Netcode fast retransmit on packet loss", "Improved netcode performance") make no mention of `bandwidthAlg`. — [SPOTREP #00120](https://dev.arma3.com/post/spotrep-00120)
- **Community config (paraphrased).** The gist includes `-bandwidthAlg=2` in its server line without measurements. The author notes that the network-settings section may be out of date because the netcode has since improved. — [MildlyInterested gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **Excerpt-only, source pages not identified.** A search summary said the original BI patch note described the option as affecting only the server. It also mentioned a forum poster who found things better without the parameter (in a post that seemed to confuse it with the memory allocator), and a 2015-era commenter who said it only changes how queued updates are prioritised. Candidate pages, neither retrieved: [Steam "-bandwidthAlg=2 *Fix* Losing Connection?"](https://steamcommunity.com/app/107410/discussions/0/617330406665084468/), [BI forum "Yellow chains, high CPU utilization"](https://forums.bohemia.net/forums/topic/227729-yellow-chains-high-cpu-utilization/).
- **BI-official, wiki.** The Dedicated Server page's network section warns that raising `MaxMsgSend` above the default 128 "can create Desync problems if the server's available processing and/or bandwidth can not support the higher value". In other words, network tuning that exceeds CPU headroom makes desync worse. — [Dedicated Server (Wayback 2026-06-17)](http://web.archive.org/web/20260617130649/https://community.bohemia.net/wiki/Arma_3:_Dedicated_Server)

### Inferences
- Agreement: BI says "experimental, might be better". One community config uses it, and one or two excerpt-only anecdotes go each way. No source measures it.
- **Preset value:** leave it out of "Maximum". If offered at all, put it under "Experimental network" with a note to compare desync and `#monitor` numbers with and without it under the same load.

### Gaps
- No measurement (bandwidth, desync, server FPS) of `-bandwidthAlg=2` on any version was found. The Steam and forum threads could not be fetched.

## Q6. Is the Profiling-branch executable (arma3serverprofiling_x64.exe) recommended for production servers for performance?

### Takeaway
BI presents the Profiling branch as a test channel for "PERFORMANCE binaries". BI's own notes call its contents "experimental changes that can be unstable", and several regressions specific to dedicated servers or headless clients occurred there. The large performance work (the Enfusion job system, Oct 2024) reached stable in 2.20 (June 2025), so Profiling is roughly a 6–8 month preview. The diagnostics features marked "(Profiling-only)" are for measurement, not speed. Some community admins run it in production, but no source shows that the profiling executable itself is faster than the stable one on the same version.

### Cited Findings
- **BI-official, Dedmen, Jan 2025.** "Note: Profiling branch contains experimental changes that can be unstable. Please report issues to developers, and consider switching back to stable / default branch if the issues are too severe." — [Profiling thread p.107 (Wayback 2025-02-02)](http://web.archive.org/web/20250202170530/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=107)
- **BI-official, Dedmen, 30 Oct 2024 (v6).** Added "Replaced Real Virtuality multithreading system with Enfusion's version", asynchronous and partially multithreaded AI, and multithreaded JIP queue processing. "Note: while these changes have been tested internally… They should be considered experimental." The next day (v7) several parts were removed because they "caused instability". — [Profiling thread p.106 (Wayback 2024-11-06)](http://web.archive.org/web/20241106123403/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=106&tab=comments)
- **BI-official, regressions.** Known issues and fixes include "Rare crash in PhysX (observed only on Dedicated Server)" (v13, 26 Nov 2024), "Fixed: Server crashes related to JIP Queue" (v8), and "Fixed: Server could freeze when too many network messages were received" (2.16 v19). Users also reported headless clients failing to finish connecting on 2.18.152272 when the previous build had worked. — [Profiling thread p.107 (Wayback 2025-02-02)](http://web.archive.org/web/20250202170530/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=107); [p.106 (Wayback 2024-11-06)](http://web.archive.org/web/20241106123403/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=106&tab=comments)
- **Community, compatibility.** A user reported that a profiling update broke `setObjectTextureGlobal` JIP compatibility between profiling and non-profiling players (23 Nov 2024). — [Profiling thread p.107 (Wayback 2025-02-02)](http://web.archive.org/web/20250202170530/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=107)
- **BI-official, diagnostics are the "profiling" part.** Entries tagged "(Profiling-only)" include `diag_captureSlowFrame` continuous capture, Chromium-trace export, `-networkDiagInterval` logging of publicVariable sizes, and `mpMessageDetails`. Builds are posted for "server and client, windows 64-bit, linux server 64-bit". — [Profiling thread p.106 (Wayback 2024-11-06)](http://web.archive.org/web/20241106123403/https://forums.bohemia.net/forums/topic/160288-arma-3-stable-server-218-profiling-performance-binary-feedback/?page=106&tab=comments)
- **BI-official, 2.20.** The optimizations went to Profiling first. Testing there "has been very important in testing under real-world conditions", and early versions caused crashes related to target scanning and mods. — [OPREP 2.20](https://dev.arma3.com/post/oprep-performance-optimizations-in-220)
- **BI-official, 2.22.** "Added: Option to launch Server / Profiling / Diagnostics executables" (launcher). — [SPOTREP #00120](https://dev.arma3.com/post/spotrep-00120)
- **BI-official, wiki.** The "Arma 3: Performance Profiling" page is still an empty work-in-progress stub (last edited 25 Oct 2024). — [Performance Profiling, Wayback 2026-02-13](http://web.archive.org/web/20260213230959/https://community.bohemia.net/wiki/Arma_3:_Performance_Profiling)
- **Community, pro-profiling (paraphrased).** The gist strongly suggests running the server from the `profiling` branch for possible FPS improvements not yet on stable. It says the branch stays compatible with stable-branch players and that the separate `arma3serverprofiling_x64` exe is not needed. — [MildlyInterested gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **Community (paraphrased).** XenyxNZ describes the profiling build as a public beta branch that can contain bugs, and recommends reverting to stable or an older profiling build if needed. — [XenyxNZ guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)

### Inferences
- "Profiling branch" (the Steam beta that replaces binaries with newer engine code) and "the profiling executable" (`arma3serverprofiling_x64.exe`, the build with diag commands) are different things. Any speed advantage comes from the branch running newer engine code, not from the profiling exe as such. That is an inference from the changelogs, since no BI statement compares the two exes.
- Agreement: BI (two statements) calls it experimental or possibly unstable. One community source recommends it for production, one says use with care. For a 40–80 player event server, the documented server and HC regressions are a real risk.
- **Preset value:** do not use the profiling branch or exe in the default "Maximum" preset. Offer "Profiling branch" as a separate branch selector with a stability warning and a one-click way back to stable. The panel should probably keep any headless clients on the same branch and build as the server (an inference from the HC-connection regression reported above; no source states this as a rule).

### Gaps
- No benchmark comparing `arma3serverprofiling_x64.exe` with `arma3server_x64.exe` on the same build was found.
- The 2.20/2.22-era profiling thread pages (after Jan 2025) and the "Prof-Branch Change Log v2.20/v2.22" wiki pages could not be retrieved: direct fetches got 403, and the Wayback Machine has no snapshot of either changelog page on either wiki host (checked while the archive was online). - Not verified: whether `arma3serverprofiling_x64.exe` ships on the stable 2.22 branch (the 2.22 launcher option to start "Profiling" executables suggests it might), and whether it differs from `arma3server_x64.exe` only by diagnostics or also by engine code.

## Q7. Remaining parameters: -loadMissionToMemory, -maxMem, -noLogs, -setThreadCharacteristics, -cpuAffinity / -cpuMainThreadAffinity (and related harmful flags)

### Takeaway
`-loadMissionToMemory` is a documented server-only CPU saving with no reported downside. Include it. `-maxMem` is auto-set to about 80% of physical RAM, and BI advises not setting it. `-noLogs` gives up crash diagnostics for an unmeasured gain. `-setThreadCharacteristics` carries a BI warning that it can freeze Windows Server. `-cpuAffinity` and `-cpuMainThreadAffinity` (new in 2.22) are expert tools for co-located headless clients or hybrid and multi-CCD CPUs, and setting `-cpuAffinity` disables `-enableHT`.

### Cited Findings
- **BI-official, wiki.** `-loadMissionToMemory`: "Server will load mission into memory on first client downloading it. Then it keeps it pre-processed pre-cached in memory for next clients, saving some server CPU cycles." Used in the gist's server line. — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters); [gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **BI-official, wiki.** `-maxMem`: the 1024 MiB minimum is hard-coded, and on 64-bit Windows with the 64-bit game the maximum is "(physical memory * 4) / 5". "Without the -maxMem parameter the engine attempts to set this parameter internaly to a reasonable value often defaulting to max values". "Setting maxMem to 2000 does not mean that the game will never allocate more… In general, it makes sense not using this parameter at all and only resort to it in case you experience issues with memory." The file cache is excluded from the limit. Until 2.14 the Linux server parsed the value as signed. — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official, wiki.** `-maxFileCacheSize` (since 2.14) sets the RAM file cache. The default "was either maxMemory - 448 MB or… limited to max 2048 MB", "Setting lower than 1 GB is not recommended", and the minimum is 512 MB. — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **Community.** A server admin running `-maxMem=8192 -cpuCount=8 -enableHT -hugepages -filePatching -bandwidthAlg=2` saw RAM climb past maxMem. The thread traced it to filePatching and extDB3 configuration, not the memory flags. That excerpt comes from a search summary. — [BI forum "Dedicated server flooding the RAM after mission start" (not retrieved)](https://forums.bohemia.net/forums/topic/216127-dedicated-server-flooding-the-ram-after-mission-start/)
- **BI-official, wiki.** `-noLogs`: "Be aware this means none errors saved to RPT file (report log). Yet in case of crash the fault address block info is saved." The wiki states no performance figure. — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **BI-official, wiki.** `-setThreadCharacteristics` (since 2.10) "Registers the game's executable as 'Game' in Windows for performance improvements." Warning: "This flag can freeze the whole Operating System if running Windows Server!" XenyxNZ repeats the warning. — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters); [XenyxNZ guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md)
- **BI-official, 2.22.** "Added: -cpuAffinity command-line parameter" and "Added: -cpuMainThreadAffinity command-line parameter". The wiki shows `-cpuAffinity=0xFF` and says "To see if the value was applied correctly, check the rpt file". For `-cpuMainThreadAffinity=0x01`, "If the value could not be applied a message will be logged to the rpt file". `-enableHT` "is overridden if -cpuCount or -cpuAffinity are used". — [SPOTREP #00120](https://dev.arma3.com/post/spotrep-00120); [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)
- **Wiki-community, Dedicated Server page.** When a headless client and the dedicated server share one Windows machine, "it may be beneficial to set processor affinity to prevent execution intensive threads from being scheduled across the same (v)CPUs". It warns: "Do not use this if you do not know what you are doing, as performance may be strongly impacted. The operating system will generally schedule threads efficiently". The older method shown is `CMD /C START /AFFINITY 0xF3 arma3server.exe`. — [Dedicated Server (Wayback 2026-06-17)](http://web.archive.org/web/20260617130649/https://community.bohemia.net/wiki/Arma_3:_Dedicated_Server)
- **Community (paraphrased).** XenyxNZ calls `-cpuAffinity` and `-cpuMainThreadAffinity` advanced options that can help on CPUs with multiple CCDs or with P- and E-cores. It says they ignore the CPU count, Extra threads and Hyper-Threading settings and can worsen performance without understanding of the CPU topology. The gist says it is unclear whether manual affinity improves FPS, and that some admins report up to about 10% from setting process priority to High. — [XenyxNZ guide](https://github.com/XenyxNZ/Arma-3-Performance-Guide/blob/main/README.md); [gist](https://gist.github.com/MildlyInterested/5ecefd1ad75522eae1fa5e8f4b839fd3)
- **BI-official, wiki, harmful flag.** `-disableServerThread` is an "Option to disable the server send messaging thread in case of random crashing (may also decrease performance of server on multicore CPUs)". — [Startup Parameters (Wayback 2026-06-17)](http://web.archive.org/web/20260617124651/https://community.bohemia.net/wiki/Arma_3:_Startup_Parameters)

### Inferences
- **Preset values** for a "Maximum" preset on a 6+ core, 32 GB+ Windows host (these are inferences that combine the findings above):
  - **Include:** `-loadMissionToMemory`.
  - **Include, conditional:** `-hugePages`, only if SeLockMemoryPrivilege is verified for the service account (Q3).
  - **Moderate:** `-limitFPS=100`, plus `idleFPSLimit` in server.cfg on 2.22 (Q4).
  - **Leave out:** `-cpuCount` and `-exThreads` (Q1); `-maxMem` (auto is about 25.6 GB on 32 GB and 51 GB on 64 GB, per the 4/5 rule); `-maxFileCacheSize`; `-malloc` (default `tbb4malloc_bi`; mimalloc is opt-in from the DLLs present, Q3); `-bandwidthAlg=2` (Q5); `-setThreadCharacteristics` (block it outright on Windows Server editions); `-disableServerThread`; `-noLogs` (keep the RPT for crash triage; there is no evidence of a measurable gain).
  - **Opt-in toggles:** `-enableHT` (off by default, Q2), `-cpuAffinity` and `-cpuMainThreadAffinity` (only to separate server and HC cores on one box, or on hybrid or multi-CCD CPUs). The panel should block `-enableHT` together with `-cpuCount` or `-cpuAffinity`.
  - **Branch:** stable. Profiling is opt-in (Q6).
- The panel can confirm that `-cpuAffinity` and `-cpuMainThreadAffinity` were applied by parsing the RPT, because BI says success or failure is logged there.
- Process priority "High" (gist, about 10%, anecdotal) is an OS setting, not a launch parameter. If offered, it is unproven and separate from `-setThreadCharacteristics`.

### Gaps
- No measurement of `-noLogs` or `-loadMissionToMemory` effect on server FPS was found.
- No server benchmark of `-cpuAffinity` or `-cpuMainThreadAffinity` (introduced 2.22, Aug 2026) was found. Evidence is limited to BI's description and one community guide.
- How `-maxMem` auto-detection behaves next to locked large pages on the same host was not covered by any source.
- Server-host knowledge bases (Nitrado, GTX Gaming, 4netplayers, Host Havoc) and FASTER docs were not reached within the research budget. Search snippets showed hosts mainly documenting where to enter parameters, plus warnings that unsupported options can stop the server from starting.
