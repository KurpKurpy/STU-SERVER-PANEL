# Phase 2: Server Connection Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an admin pairs a Windows agent with the panel, registers the Arma 3 install and one server profile, then starts, stops, restarts and force-stops the real dedicated server from the browser. The server page shows live status (checked through A2S), the live RPT log, resource stats with short history charts, and the historic log files.

**Architecture:**
- **New `src/Agent`** (a .NET 10 worker; namespace `ServerAgent`, exe `ConsoleAgent.exe`) dials out to the panel's SignalR hub `/hubs/agent`, authenticated by a paired key. It supervises `arma3server_x64.exe`, polls A2S, tails the RPT and samples resources.
- **New `src/Contracts`** holds the message records and `IAgentClient`, which both sides compile against.
- **Panel:**
  - calls the agent with SignalR client results;
  - keeps live state in a singleton `AgentRegistry`;
  - pushes status, resources and console lines to the browser over a cookie-authenticated `/hubs/ui`;
  - re-checks every UI connection's access on the stamp interval.
- **Not in Phase 2:** RCon or console command input, headless clients, SteamCMD, mission or file deployment, the `Job` table.

**Tech Stack:**
- **Backend:** .NET 10, ASP.NET Core minimal APIs and SignalR, EF Core Sqlite.
- **Packages** (all pinned `10.0.15`): `Microsoft.AspNetCore.SignalR.Client` (Agent and Panel.Tests), `Microsoft.Extensions.Hosting.WindowsServices` (Agent and Panel).
- **Tests:** xUnit (`tests/Agent.Tests`, `tests/Panel.Tests`) and a fake Arma server exe (`tests/FakeArmaServer`).
- **Frontend:** React 19, TanStack Query 5, Tailwind v4, Phosphor icons, `@microsoft/signalr`.

## Global Constraints

**Toolchain and process**
- **.NET:** the 10 SDK at `C:\Program Files\dotnet\dotnet.exe`. PATH resolves to an x86 host, so always call this one. Pin every Microsoft package to `10.0.15`; NuGet otherwise picks .NET 11 packages.
- **Panel dev server:** stop it (preview `panel`) before `dotnet test`, because it locks `Panel.exe`. Restart it afterwards.
- **No git:** there is no repository and the user hasn't asked for one. Keep the ledger by hand, as in Phase 1, and skip commit steps.
- **Final review:** the review-package script needs git, so the reviewer gets the file list instead.
- **EF migrations:** `"C:\Program Files\dotnet\dotnet.exe" tool run dotnet-ef migrations add <Name> -p src/Panel`.

**Machines and paths**
- This PC is the dev machine. The real server box is a separate machine, and deploying there is a separate plan.
- **Dev test server:** `K:\Steam\steamapps\common\Arma 3\arma3server_x64.exe`. Treat K: as read-only:
  - nothing in Phase 2 may write under K:;
  - every dev `server.cfg` sets `BattlEye = 0;` (BattlEye would write into the install's `BattlEye` folder).
- **Dev agent data root:** `D:\13th_server_dev`, with areas `profiles\` and `configs\`.
- **Dev game ports:**
  - 2302 for the end-to-end profile;
  - 2402 for the spike;
  - tests pick free ports at random from 40000 upwards.

**Security boundary (design §5.3), enforced in the agent, never only in the panel**
- **Executables:**
  - the agent launches only `arma3server_x64.exe` or `arma3serverprofiling_x64.exe`;
  - the exe must sit directly inside an install root from the agent's own list: `Agent:InstallRoots`, or Steam-library detection when that's empty;
  - a path the panel sends only *selects* among those roots.
- **Arguments:**
  - passed through `ProcessStartInfo.ArgumentList`, never a shell;
  - `-port`, `-config`, `-cfg`, `-profiles` and `-name` are generated by the agent;
  - custom args must pass `Arma3LaunchArgs.Validate`, an allowlist of names whose values can't carry paths.
- **Paths:**
  - every path is `(area, relativePath)`, resolved by `Areas.Resolve`;
  - rooted paths, `..`, anything outside the area, and any reparse point (junction or symlink) inside the area are rejected;
  - install areas are read-only.
- **The panel can't set agent paths.** The setup wizard shows the agent's paths and their checks, and tells the admin which `appsettings.json` key to change.

**Data**
- **Ids and time:** ids are GUIDs and timestamps are UTC `DateTime`, as in Phase 1. Two migrations: `Phase2Agents` (Task 6) and `Phase2Servers` (Task 7).
- **Raw `server.cfg`:**
  - stored encrypted with Data Protection, purpose `"profile.serverCfg"`;
  - returned only to `profiles.manage`;
  - never put in audit details, logs or `/api/servers`.
- **Agent key:**
  - format `<agentId:N>.<base64url of 32 random bytes>`;
  - the panel stores only the hex SHA-256 of the secret part, compares it in fixed time, and shows the key once.

**Permissions (catalog additions; Owner passes everything)**

| Key | Label | Seeded to |
|---|---|---|
| `server.control` | Start, stop and restart the server | Server Administrator |
| `server.forceStop` | Force-stop the server | Server Administrator |
| `profiles.manage` | Set up server profiles | Server Administrator |
| `logs.view` | See the live console and server logs | Server Administrator, Zeus |
| `agents.manage` | Pair server agents and register installs | (Owner only) |

**Status truth**
- **Agent states:** `Offline`, `Starting`, `Online`, `NotResponding`, `Stopping`, `Error`.
- **Online:** only while the process is alive and A2S answers on game port + 1.
- **Starting:** alive, but A2S hasn't answered since launch.
- **NotResponding:** it was Online, then missed 3 queries in a row.
- **Panel-only `unknown`:** whenever the profile's agent isn't connected, including just after a panel restart. Never show a last-known state.
- **Never killed by restarts:** the agent doesn't kill the server when the agent or panel restarts, and re-attaches by PID plus start time.

**API conventions:** as in Phase 1. Errors use `{ code, message }`, unsafe `/api` methods need `X-Console: 1`, and unknown `/api/*` routes return 404 JSON. SignalR on both hubs uses JSON with `JsonStringEnumConverter`.

**Frontend (design §9 as restyled)**
- **Tokens:** semantic classes only (`bg-surface`, `bg-console`, `text-accent-text`, `text-text-muted`, `border-line`, `bg-tint`); `<html data-accent="red">`.
- **Type:** stencil titles through `Panel` or the `display` utility; Barlow UI text; IBM Plex Mono only for figures, IDs, times and log lines.
- **Icons:** Phosphor only (`*Icon` names), regular weight.
- **Shape:** square cards (`Panel`), with the primary button as the only cut-corner control.
- **Status:** always a word on a `StatusBlock`. Tones:
  - online → ok;
  - starting, stopping, notResponding → warn;
  - error → bad;
  - offline, unknown → off.
- **Rules:**
  - 4.5:1 contrast;
  - 44 px targets on `pointer: coarse`;
  - visible focus;
  - reduced motion respected;
  - no page-level horizontal scroll at 375 px;
  - wide tables and log views scroll inside their own box.
- **Nothing fake:**
  - no RCon input box, player list or Update buttons;
  - the console panel says it's read-only;
  - a stat that can't be measured shows "—" with a reason in its label.

## Rulings made in this plan

Approved by the user on 2026-11-19 and written into the design doc. Carry them into the ledger as `Plan: Ruling: …`:

1. **Wizard paths:** the wizard (design §11) shows the agent-owned paths read-only, with checks. It doesn't edit them, because design §5.3 keeps area roots on the agent so a compromised panel can't redirect writes. *Cost if wrong:* changing a path needs an edit on the box.
2. **`profiles.manage` now, not in Phase 3:** the minimal profile has to be created by someone, and "Manage server profiles" is that permission. Phase 3 gives it the structured editors.
3. **`Profile.BasicCfg` column added:** design §11 asks for a `basic.cfg` import in Phase 2, and §8 has no column for it. Phase 3 can fold it into `SettingsJson`.
4. **No `Job` table and no `ServerInstall.Branch` yet:** nothing in Phase 2 is a long job or picks a branch. They arrive with the first phase that uses them (Phase 4 or 5). *Cost:* one later migration.
5. **Graceful stop without RCon:** `CloseMainWindow()`, then kill the process tree after `Agent:StopTimeoutSeconds` (default 60). RCon `#shutdown` replaces the first step in Phase 7.
6. **`NotResponding` state** added to design §5.3's list, so a hung server isn't shown as Online or Starting.
7. **Live data stays in memory:** console lines (2,000 per profile) and resource history (the agent's last 15 minutes) are in-memory buffers. Historic logs come from the RPT files on the Logs page.
8. **Join password:** address and port are shown to `server.view`. The join password, and `server.viewJoinInfo`, arrive in Phase 3 when the structured `server.cfg` editor separates it.

**Rules**
- **Per-profile lock:** a `SemaphoreSlim(1)` per profile id, held by Start, Stop and Restart only while they check and change state (see the Stop rules below).
- **Start refuses** with a `StartResult(false, message)` when:
  - the profile is running or stopping;
  - `InstallPath` isn't one of `Areas.InstallRoots` (full path, case-insensitive);
  - `Executable` isn't allowlisted, or is missing from the install root;
  - `Arma3LaunchArgs.Validate` fails;
  - the game port or query port is in `IPGlobalProperties.GetActiveUdpListeners()`;
  - another tracked profile's `[port, port+4]` overlaps.
- **Start sequence:**
  1. Write config files atomically (temp file plus move).
  2. Create `profileDir`.
  3. `Process.Start` with `UseShellExecute=false`, `WorkingDirectory` = install root, args through `ArgumentList`.
  4. Persist the state file.
  5. Status → `Starting`.
  6. Start the per-profile query loop (`QueryIntervalSeconds`).
- **Query loop:** an answer → `Online` with `Query`. No answer while never online → `Starting`. 3 misses in a row after being online → `NotResponding`.
- **Exit:** on `Process.Exited`, a requested stop → `Offline`. Otherwise → `Error("Server exited unexpectedly (exit code N)")` with `ExitCode`. Remove the entry from the state file.
- **Stop** sets `Stopping`, calls `CloseMainWindow()` and returns `Ok` at once. A background task waits `StopTimeoutSeconds`, then calls `Kill(entireProcessTree: true)`.
- **Restart** returns `Ok` once the state is `Stopping`. The background task waits for the exit, then starts again; if that start fails, the status is `Error` with its message.
- **ForceStop** never waits on the profile lock: it kills at once, and any background stop sees the exit.
- **The lock** is held only while a command checks and changes state, never across the stop wait. A Start during `Stopping` is therefore refused at once, not queued.
- **Handlers stay short:** every agent command returns within a few seconds, and nothing awaits a process exit inside a SignalR handler, so `ReadFile` never stalls behind a stop.
- **State file:** `<DataRoot>\agent-state.json`, a map of `profileId → { pid, startedAt, slug, port, installPath, executable }`.
- **Re-attach:** for each entry:
  - `Process.GetProcessById(pid)`;
  - `ProcessName` must equal the exe name without `.exe`;
  - `|StartTime.ToUniversalTime() − startedAt| < 2 s`;
  - then supervise it again (`EnableRaisingEvents`, query loop).

  Otherwise drop the entry and emit `Offline` with `Error = "Stopped while the agent was not running"`.
